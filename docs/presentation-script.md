# 발표 대본 — "확정 전에는 코드를 짜지 않는다"

> 약 12분 + 질문 5분. 듣는 사람: 기획(PO)·디자인·개발.
> 화면 두 개를 띄워 둔다 — ① https://prototype.dotdotslash.me/ ② GitHub PR 목록.
> **굵은 글씨**는 꼭 말할 문장, `[화면]`은 그때 보여 줄 것.

---

## 1. 문제 (1분 30초)

`[화면] 없음 — 말로 시작`

지금 우리는 기획이 어느 정도 나오면 바로 실제 코드로 만들어 보면서 다듬습니다.
그런데 실제 코드로 만들어 보면 **DB까지 같이 바뀝니다.** 방향이 틀리면 화면만이 아니라 테이블·API·마이그레이션까지 되돌려야 합니다.

반대로 피그마로 먼저 확정하면, 화면은 정해지는데 **화면에 안 보이는 규칙** — 누가 볼 수 있는지, 실패하면 어떻게 되는지,
숫자는 얼마인지 — 이 빈칸으로 남습니다. 그 빈칸은 개발 도중에 발견되고, 그때마다 다시 회의합니다.

그래서 제안합니다. **확정 전에는 실제 코드를 짜지 않고, 버리는 프로토타입과 명세로 먼저 확정한다.**

---

## 2. 방식 한 장 (1분 30초)

`[화면] GitHub README 의 흐름도`

1. 누구나 프로토타입 초안을 만듭니다. AI로 만들어서 한 시간이면 됩니다.
2. PR을 올리면 **미리보기 주소가 자동으로** 생깁니다. 각자 시간 날 때 열어 보고 코멘트를 남깁니다.
3. 기획·디자인·개발 담당이 각자 자기 쪽을 보고 Approve하면 **확정**입니다.
4. 확정되면 디자인·개발·문서가 **동시에** 출발합니다. 규칙은 정해졌으니 서로 기다릴 필요가 없습니다.

**원칙은 하나입니다 — 명세가 정본이다.** 프로토타입은 버리는 코드라서, 둘이 어긋나면 명세를 따릅니다.

---

## 3. 데모 ① 확정본 둘러보기 (2분)

`[화면] https://prototype.dotdotslash.me/`

예시로 가상의 동네 책방 서비스 "책숲"을 만들어 봤습니다. 독자 앱과 서점 사장님 앱, 두 개입니다.

- 목록이 **기반**과 **기능**으로 나뉘어 있습니다. 이 목록은 손으로 만든 게 아니라 각 명세의 머리말에서 자동으로 만들어집니다.

`[화면] 북클럽 모임 → 화면 보기`

- 독자로 들어가서 모임을 신청해 봅니다. **포인트가 얼마 빠지는지 확정 버튼 앞에** 보여 줍니다.
- 위쪽 점선 바가 **보기 전환 바**입니다. 제품 화면이 아니라 리뷰 도구입니다.
- 브랜드를 "책숲 파트너"로 바꾸면 같은 기능의 **사장님 화면**으로 바뀝니다. 테마도 라이트·다크로 바꿔 볼 수 있습니다.

`[화면] 명세 읽기`

- 명세는 한 화면입니다. 결정 · 권한 · 상태 변화 · 숫자 · 기존 코드와의 관계 · 남은 질문.
- **"하지 않기로 한 것"**도 적습니다 — 현장 결제는 안 한다, 왜냐면. 인수인계에서 제일 자주 사라지는 게 이겁니다.
- **"남은 질문"**에는 담당과 "구현을 막는지"가 붙습니다. 막지 않는 건 미뤄도 착수할 수 있습니다.

## 4. 데모 ② 리뷰 중인 기능 PR (2분)

`[화면] PR #6 책 퀴즈`

이건 지금 리뷰 중인 상태를 그대로 둔 예시입니다.

- PR을 올리자 봇이 **미리보기 링크**를 코멘트로 달았습니다. 리뷰어는 이 링크만 열면 됩니다.
- 본문에 "확인받고 싶은 것"과 "남은 질문"만 있습니다. 코드 설명은 없습니다.
- 이 PR은 퀴즈 탭을 메뉴에 추가했습니다. 그래서 **화면 비교**에 다른 화면들까지 "달라짐"으로 잡혔습니다 —
  기능 하나 추가가 앱 전체 메뉴를 바꾼다는 걸 리뷰어가 놓치지 않습니다.

## 5. 데모 ③ 디자인 시스템 PR (2분)

`[화면] PR #7 태그 글자 대비`

"그럼 전체 구조나 디자인 시스템은 어떻게 하냐"가 이 방식의 약점이었습니다.

- 모든 화면이 **디자인 시스템 파일 하나**와 **앱 셸 하나**를 가져다 씁니다.
- 그래서 이 PR은 토큰 파일 두 개만 바꿨는데, 미리보기에서는 **모든 화면이 새 색으로** 다시 그려집니다.

`[화면] 코멘트의 화면 비교 링크 → 갤러리`

- main과 이 PR을 **브랜드 × 테마 × 모바일·데스크톱**으로 전부 찍어 나란히 놓습니다.
- 디자이너는 "의도한 화면만 바뀌었나"를 여기서 한 번에 봅니다. 하나씩 열어 볼 필요가 없습니다.
- 여기서 확정한 값은 제안입니다. 확정되면 실제 디자인 시스템 패키지에 반영합니다.

## 6. 실제 코드와 다른 저장소인데? (1분 30초)

`[화면] GitHub context/ 폴더`

프로토타입 레포는 제품 코드와 떨어져 있어서, 그냥 두면 "이미 있는 기능", "비싼 것", "못 바꾸는 것"을 모르고 그립니다.

- `context/` 폴더에 **제품 현황 · 제약 · 용어집 · 공용 규칙의 사본**을 둡니다.
- **정본은 제품 레포**입니다. 코드를 고치는 사람이 같은 PR에서 현황을 고치고, 머지되면 이 레포로 자동 PR이 옵니다.
- 명세의 「기존 코드와의 관계」에 재사용·신규·충돌을 적습니다. **개발 담당은 리뷰 때 이 표만 보고 비용을 말합니다.**
- 공용 규칙(개인정보 기본 비공개, 운영자 조작은 감사 기록 등)은 모든 레포를 아우르는 한 벌이고, 폴더 규칙이 덮을 수 없습니다.

---

## 7. 시작 제안 (1분)

- **도메인 하나로 1~2주** 먼저 해 봅니다.
- 재는 것은 두 가지입니다 — **확정까지 걸린 시간**, **확정 뒤에 뒤집힌 규칙 수**.
- 전제: 명세가 정본이라는 데 동의 · 도메인마다 기획·디자인·개발 담당 · 사업 결정의 최종 결정권자 · 모두 AI 도구 사용 가능.

**마무리 한 문장: "코드를 짜기 전에, 눌러 볼 수 있는 화면과 한 장짜리 명세로 먼저 합의하자."**

## 예상 질문

**Q. 피그마 와이어프레임이랑 뭐가 다른가?**
A. 눌러 볼 수 있고, 화면에 안 보이는 규칙을 명세로 같이 확정합니다. 그리고 디자이너가 바빠도 누구나 초안을 만들 수 있어 진행이 안 멈춥니다. 디자인은 확정 뒤 디자이너가 다듬습니다 — 프로토타입은 디자인 확정이 아닙니다.

**Q. 프로토타입 코드를 실제 개발에 재사용하나?**
A. 안 합니다. 버리는 코드입니다. 재사용하려는 순간 프로토타입을 정성 들여 짜게 되고, 그러면 다시 느려집니다. 넘어가는 건 명세입니다.

**Q. 명세 쓰는 게 일이 늘어나는 것 아닌가?**
A. 한 화면 분량이고, AI가 초안을 씁니다. 화면을 다 만든 뒤 "이 화면에서 안 보이는 규칙이 뭐냐"고 물으면 빈칸을 먼저 찾아 줍니다. 사람은 그 질문에 답하는 일만 합니다.

**Q. 현황 문서(context/)는 결국 낡지 않나?**
A. 자동으로 뽑을 수 있는 부분(기능 목록·역할·토큰·메뉴)은 제품 레포 CI가 만듭니다. 사람이 쓰는 건 "왜 비싼가·왜 못 바꾸나"뿐이고, 제품 레포 PR 템플릿에 "현황에 영향이 있나" 한 줄을 둡니다. 명세에 현황 버전이 적혀 있어서, 확정 시점에 그 사이 바뀐 게 있으면 보입니다.

**Q. 보안 — 공개 전 기획이 밖으로 나가지 않나?**
A. 이 예시는 가짜 서비스라 공개해 뒀습니다. 사내에서는 같은 구조를 비공개 저장소 + 사내 IP·인증으로 막는 정적 호스팅에 둡니다. 파일 이름이 고정이라 캐시는 끕니다.

**Q. 의견이 끝까지 갈리면?**
A. 화면 의견은 디자이너가, 규칙 의견은 기획이 정합니다. 요금·정산 같은 사업 결정은 명세의 "최종 결정권자"가 정하고, 그 전까지는 "남은 질문 — 구현을 막음"으로 둡니다.
