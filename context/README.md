# context — 실제 제품 레포의 현황

> 🧪 **예시다.** 여기 적힌 동네 책방 플랫폼 "책숲"과 그 코드는 존재하지 않는다. 실제로 쓸 때 이 폴더가 어떻게 생기고
> 어떻게 갱신되는지를 보여 주려고 가짜 내용으로 채웠다.

프로토타입 레포는 제품 코드와 다른 저장소다. 그래서 프로토타입을 만드는 사람(과 AI)이 "이미 있는 것",
"비싼 것", "못 바꾸는 것"을 모르고 화면을 그리기 쉽다. 이 폴더가 그 간극을 메운다.

| 파일 | 무엇 | 누가 갱신하나 |
|---|---|---|
| [`features.md`](features.md) | 이미 있는 기능과 그 권한·데이터 | 자동 추출 + 사람 보충 |
| [`constraints.md`](constraints.md) | 제약 — 비싼 것, 못 바꾸는 것, 재사용할 것 | 사람 (개발 담당) |
| [`glossary.md`](glossary.md) | 용어집 — 같은 것을 같은 이름으로 | 사람 (기획 담당) |
| [`rules.md`](rules.md) | 모든 레포를 아우르는 공용 규칙(개인정보·운영·화면·문구)의 사본 | 조직 공용 규칙 레포에서 자동 |

디자인 토큰과 앱 구조는 여기 두지 않는다. 그건 **프로토타입으로** 있다 — `prototypes/design-system/`,
`prototypes/app-structure/`. 다른 프로토타입이 그 파일을 직접 가져다 쓰기 때문이다.

## 어떻게 쓰나

- **만들 때**: `/prototype` 스킬은 화면을 그리기 전에 이 폴더를 먼저 읽는다. 사람도 마찬가지다.
- **명세에**: 기능 명세의 「기존 코드와의 관계」 절에 재사용·신규·충돌을 적고, 읽은 현황의 버전(아래 `현황 버전`)을 남긴다.
- **리뷰할 때**: 개발 담당은 그 절만 보고 비용을 판단한다. "이건 이미 있다 / 이건 비싸다"를 여기서 말한다.

## 현황 버전

```
제품 레포: example/chaeksup-app (가상)
커밋:     a1b2c3d (가상)
생성:     2026-10-07
```

확정할 때 명세에 적힌 현황 버전과 지금 버전이 다르면, 그 사이 바뀐 현황이 명세와 부딪치지 않는지 다시 본다.

## 동기화 — 실제로 들일 때의 모습

**정본은 제품 레포다.** 제품 코드를 고치는 사람이 같은 PR에서 현황 문서도 고친다. 프로토타입 레포는 사본을 받기만 한다.

```
제품 레포 main 머지
  → 제품 레포 CI: docs/prototype-context/ 를 다시 만든다 (자동 추출 부분)
  → 프로토타입 레포에 "context 갱신" PR 을 연다 (봇 계정)
  → 프로토타입 레포에서 머지 = 모두가 새 현황을 본다
```

자동 추출할 수 있는 것 (제품 레포의 스크립트가 만든다):

| 무엇 | 어디서 |
|---|---|
| 기능 목록·권한 | 라우트·권한 데코레이터·기능 문서 |
| 역할 이름 | 역할 enum |
| 운영이 바꾸는 숫자 목록 | 설정 테이블·어드민 화면 목록 |
| 디자인 토큰 | 디자인 시스템 패키지 → `prototypes/design-system/tokens.css` 로 |
| 앱 내비게이션 | 라우터 설정 → `prototypes/app-structure/shell.js` 의 `NAV` 로 |

자동으로 못 하는 것: `constraints.md`의 "왜 비싼가", "왜 못 바꾸는가". 이건 개발 담당이 쓴다.
그래서 제품 레포 쪽 PR 템플릿에 "프로토타입 현황에 영향이 있나" 체크 한 줄을 둔다.

> 이 예시 레포에는 위 동기화 CI가 없다(동기화할 실제 제품 레포가 없어서). 형태만 보여 준다.
